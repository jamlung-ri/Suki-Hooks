## What This Measure Captures

**CM-09 Note Inaccuracy Rate** is the presence of clinically inaccurate or fabricated content in an AI-generated note — information that was not stated in the encounter or is factually wrong. It is distinct from CM-08 (Note Completeness), which measures what was *left out*. Together, they cover the two principal failure modes of ambient documentation:

| Error type | Canonical measure | Example |
|---|---|---|
| Missing information | CM-08 — Completeness and Omission Rate | Medication dose mentioned in visit not captured in note |
| Wrong or invented information | CM-09 — Note Inaccuracy Rate | Negation reversed: "patient denies chest pain" → "patient reports chest pain" |

**Why this matters for Suki's value story:** Hallucinations and inaccuracies are less frequent than omissions, but more dangerous per event because wrong information is harder to catch than missing information — a note that says nothing about chest pain is an omission; a note that inverts the negation is a patient safety risk. Published rates range from 3–36% of notes depending on error definition (Baker 2023: 36%; Palm 2025: 31%; Kernberg 2023: 3.2% incorrect facts). Bundy 2024 identified negation reversal as a specific high-risk subtype.

## Current Suki Hooks and Data Available

Suki's API provides several artifacts that can support note inaccuracy measurement today, without EHR integration.

### What Suki exposes natively (H1 + H15)

| Artifact | API endpoint | What it enables |
|---|---|---|
| Full transcript | `GET /session/{id}/transcript` | Ground truth of what was said; basis for any note comparison |
| Note content with evidence links | `GET /session/{id}/content` | Each note section includes `source_transcripts[]` — the specific transcript phrases that produced each sentence |
| Structured diagnoses | `GET /session/{id}/structured-data` | Machine-readable ICD-10/IMO codes generated from conversation |
| Session audio | `GET /session/{id}/recording` | Raw audio for re-review; retained 30 days |

**The key primitive is `source_transcripts[]`.** Every section of the generated note maps back to the specific transcript segments that produced it. This makes transcript-to-note auditing tractable at scale without listening to audio: an auditor or LLM judge can compare the cited transcript text to the note sentence and flag hallucinations, inversions, or additions.

### Measurement supported right now

- **Hallucination rate** — flag note sentences where `source_transcripts[]` evidence does not support the claim
- **Addition error rate** — identify note content that has no corresponding transcript evidence
- **Negation error detection** — automated or human check for inverted polarity between transcript and note
- **ICD-10 fidelity** — compare structured diagnoses generated by H3/PBC against the conversation context

## Missing or Aspirational Hooks

The following capabilities would substantially improve note inaccuracy measurement but are not currently available as documented API endpoints.

| Missing capability | Why it matters |
|---|---|
| **Physician-edited note** (post-accept, pre-sign) | The physician's version after edits = the implicit ground truth for inaccuracy |
| **Edit diff / change log** | Which words, sentences, or sections the physician changed reveals where Suki made errors |
| **In-app edit events** (character-level or section-level) | Would support real-time, note-level error rate computation without manual review |
| **Note insertion / writeback timestamp** | Needed to close the session → EHR note lifecycle; currently inferred, not measured directly |

## EHR-Side Data Needed

For health systems with EHR integration, the following fields close the feedback loop:

| Data element | Purpose | Vendor examples |
|---|---|---|
| Final signed note text | Gold standard to diff against Suki draft | Epic `HNO_NOTE_TEXT`; Cerner `clinical_event.RESULT_VAL` |
| Note version history / edit audit trail | Reconstructs physician edits between Suki output and final note | Epic NoteActivity; EHR audit log table |
| Note signature timestamp and signatory user | Confirms the physician reviewed and accepted the note | Epic `HNO_NOTE.SIGN_INST` |
| Encounter-to-note linkage | Joins Suki `session_id` to EHR note record | EHR encounter ID, MRN, or CSN |

Without the EHR's note version history, there is no programmatic way to know what the physician changed. The Suki draft and the EHR final note must both be present to compute an accuracy measure at scale.

## Human Rating and LLM-as-Judge

### Validated instruments

The two most relevant instruments for note quality rating in this domain are:

- **PDQI-9** (Physician Documentation Quality Instrument): 9-item, 5-point Likert; includes an *Accuracy* subscale specifically designed to flag fabricated or incorrect content. Originally designed for human notes; widely used in simulation studies.
- **PDSQI-9** (Provider Documentation Summarization QI): Adapted for AI-generated notes. Afshar 2025b validated an LLM-as-judge implementation of PDSQI-9 against physician ratings — correlation was sufficient for research-grade use, making fully automated rating feasible.

### Suggested evaluation design

**For a small, rapid pilot** using existing Suki sessions:

1. Pull 50–100 completed session transcripts and note pairs using the `source_transcripts[]` payload.
2. Ask 2–3 physician raters to score each note's Accuracy domain using the PDQI-9 rubric, flagging specific sentences.
3. Run an LLM-as-judge prompt (Claude or GPT-4) using the same rubric on the same pairs.
4. Compute inter-rater agreement and human-LLM agreement as a calibration step.
5. If LLM agreement is acceptable (r ≥ 0.7), scale automated scoring to the full session corpus.

## The Missing Feedback Loop

This is the central structural gap. Suki generates a note. The physician reviews, edits, and signs it. The physician's edits are the most direct signal of where Suki was wrong — but Suki never sees those edits.

```
Suki draft ──────► Physician review ──────► Final signed note (EHR)
     │                                            │
     └──────────── [missing link] ────────────────┘
                     edit diff
```

**What Suki currently has:** the draft (transcript + generated note).
**What Suki does not have:** the physician's edits, the final note, or the diff between them.

Closing this loop requires either:
- **An EHR integration** that captures note version history and feeds it back to Suki's analytics pipeline, or
- **A contractual data-sharing provision** in future customer agreements requesting note edit logs or final note text for evaluation purposes.

Until this loop is closed, note inaccuracy can only be measured through simulation studies or one-off rater exercises — not as a continuously monitored operational metric.

## Open Questions for Suki

These are specific data-access questions, not broad capability questions:

1. Does Suki's platform retain the pre-edit version of the note after a physician makes changes in the Suki interface (before writing back to the EHR)?
2. Are character-level or section-level edit events logged between Suki note generation and provider acceptance?
3. For EHR-integrated deployments, does Suki receive any confirmation that the note was inserted or signed — and does that confirmation include a timestamp or any note-content echo?
4. Can Suki's `source_transcripts[]` payload be used as the evidence basis for an LLM-as-judge evaluation, or are there data use constraints that would prevent this?
5. Are there pilot customers where Suki has access to note audit data (edit history, final note) that could support a small validity study?
