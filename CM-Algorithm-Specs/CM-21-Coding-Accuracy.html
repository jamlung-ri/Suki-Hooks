Canonical Measure Algorithm Card

CM-21 — Coding Accuracy

NB — Net Benefits Coding Accuracy Operationalizations: ICD-10 Coding Depth  ·  ICD-10 Suggestion Match Rate  ·  Denial Rate

Measure Overview

Construct
Documentation-driven coding quality — three operationalizations
↑ Higher is better (1, 2) ↓ Lower is better (3)

Coding accuracy captures whether clinical documentation supports correct, complete coding of the patient encounter. Suki adoption may improve coding by generating more complete transcripts that surface diagnoses and complexity levels a provider might otherwise omit when documenting under time pressure.

The three operationalizations measure different facets of coding quality: depth (how many codes per encounter), accuracy (how well Suki’s suggestions match what was billed), and payer validation (whether higher coding produces more denials). Algorithm 2 is the only one where Suki contributes primary data.

Three Operationalizations — See Algorithms Below
1ICD-10 diagnosis codes per encounter  —  proxy for documentation completeness  ↑ Higher is better
2ICD-10 suggestion match rate (%)  —  Suki-native accuracy signal  ↑ Higher is better
3Level 4–5 denial rate (%)  —  payer validation of coding uplift  ↓ Lower is better
⚠ Cross-Cutting Ambiguities
  • More codes ≠ better coding. ICD-10 coding depth (Algorithm 1) is a completeness proxy, not a direct accuracy measure. Very high code counts can signal overcoding. Always read alongside denial rate (Algorithm 3) to confirm additional codes are accepted by payers.
  • Case mix confounding. A shift toward more complex patients will raise both ICD-10 code counts and E/M levels independently of Suki. Use within-provider pre/post comparisons and flag known panel changes during the analysis window.
  • Algorithm 2 requires a pipeline not in the standard data pull. Comparing Suki’s suggested codes to final billed codes requires encounter-to-claim linkage. Suki may also return IMO codes that need mapping to ICD-10 before comparison. Confirm pipeline availability before planning work that depends on Algorithm 2.
  • Denial reason codes are required for Algorithm 3. Not all denials are coding-related. Distinguish coding denials from authorization and eligibility denials using denial reason codes. A rising overall denial rate driven by authorization changes is not a Suki signal.

Algorithms

1 ICD-10 Coding Depth ↑ Higher is better Diagnoses per encounter

Counts the average number of distinct ICD-10 diagnosis codes assigned per completed encounter. More codes per encounter indicates documentation is capturing more diagnoses per visit — a proxy for completeness, not direct accuracy. Pair with Algorithm 3 (Denial Rate) to confirm that additional codes are accepted by payers.

Units in this Algorithm
Primary
ICD-10 diagnosis codes per encounter
Count of distinct ICD-10 codes assigned per completed encounter. Averaged per provider per reporting month, then averaged across the cohort. icd10_codes_per_enc from the Suki EHR data pull is the preferred field.
Secondary
Active providers in the cohort
Providers with ≥1 completed Suki session in the month and past the onboarding ramp (default: 30 days).
⚠ This is a completeness measure only. Do not use it as a standalone accuracy measure. A provider with 6 codes/encounter and a 0% denial rate is a stronger signal than one with 8 codes and a rising denial rate.
Cohort Average=∑ (avg ICD-10 codes / encounter per provider, in the month)Number of active providers in the cohort
Reporting grain: one value per cohort per calendar month Pre / post boundary: each provider's Suki adoption date (first completed session) Exclude: onboarding ramp (default 30 days) Data source: EHR — icd10_codes_per_enc (Epic / Cerner)
Pseudocode
For each calendar month M: active_providers = providers with ≥1 completed Suki session AND past ramp period For each provider p in active_providers: icd10_per_enc[p] = avg ICD-10 codes per encounter for provider p in month M (from EHR: icd10_codes_per_enc) dashboard_value[M] = MEAN( icd10_per_enc[p] for p in active_providers )
2 ICD-10 Suggestion Match Rate ↑ Higher is better Suki Native Data Suki-to-billed code agreement

The only CM-21 algorithm where Suki contributes the primary signal. Compares AI-generated ICD-10 codes from the Suki structured-data endpoint to final billed codes from the EHR claim record. A higher match rate indicates Suki’s coding suggestions are accurate and align with what clinicians ultimately bill. Afshar 2025b (RCT, n=66) found statistically significant coding improvement (p < 0.001). A mature implementation should approach 85–90% match rate.

Units in this Algorithm
Primary
ICD-10 suggestion match rate (%)
For each completed encounter, count the Suki-suggested ICD-10 codes that also appear in the final billed codes. Divide by total billed codes.
⚠ Pipeline dependency: Requires encounter-to-claim linkage between the Suki API and EHR claims records — not part of the standard Suki EHR data pull. Suki may return IMO codes; an IMO → ICD-10 mapping step is needed before comparison. Confirm pipeline availability before planning work that relies on this algorithm.
Secondary
Early-use vs. mature-use trajectory
Match rate is expected to increase over time as providers become more familiar with reviewing and accepting Suki’s suggestions. The comparison is early-use period vs. mature-use period rather than a fixed pre/post adoption split.
⚠ Some code discrepancies are intentional — physicians or billing staff may legitimately add or remove codes during final review. A match rate of 100% would indicate codes are accepted without clinical review, which is not the goal.
Match Rate=Suki-suggested ICD-10 codes that appear in final billed codesTotal billed ICD-10 codes for the encounter
Computed per encounter; averaged across all encounters in the reporting period Data source A: Suki API — GET /session/{id}/structured-data (AI-generated ICD-10 codes) Data source B: EHR claim record — final billed ICD-10 codes per encounter Join key: encounter ID (must be passed to Suki at session creation for linkage) IMO → ICD-10 mapping step required if Suki returns IMO codes
Pseudocode
For each reporting period P (e.g., first 90 days of use vs. days 90–180): For each completed encounter E in period P: suki_codes[E] = ICD-10 codes from Suki structured-data endpoint (after IMO → ICD-10 mapping if needed) billed_codes[E] = ICD-10 codes from EHR claim record for encounter E match_count[E] = | suki_codes[E] ∩ billed_codes[E] | match_rate[E] = match_count[E] / | billed_codes[E] | period_match_rate[P] = MEAN( match_rate[E] for E in period P )
3 Denial Rate — Level 4–5 Claims ↓ Lower is better Payer validation of coding uplift

The denial rate for Level 4–5 claims serves as a payer-side validity check on coding improvement. When E/M levels and ICD-10 code counts rise after Suki adoption, a stable or declining denial rate confirms that the uplift reflects legitimate documentation-supported complexity — not overcoding. Holmgren 2026 found no increase in denials despite coding improvement, a meaningful null result. A typical Level 4–5 denial baseline is under 3%.

Units in this Algorithm
Primary
% of Level 4–5 claims denied
Denied Level 4–5 claims divided by total Level 4–5 claims submitted in the period. Focus on high-complexity claims because documentation quality most influences coding accuracy and denial risk at these levels.
⚠ Distinguish coding-related denials from authorization and eligibility denials using denial reason codes. Only coding-related denials are relevant to this measure.
Secondary
Interpretation alongside CM-20c (E/M Level Share)
This metric is a guard rail, not a standalone outcome. Read it in parallel with Algorithm 3 of CM-20 (E/M Level Improvement). A rising L4–5 share + stable denial rate = legitimate coding uplift. A rising L4–5 share + rising denial rate = possible overcoding.
⚠ Small sample sizes produce unstable denial rates. Use quarterly aggregation or a rolling 90-day window when monthly counts are below 50 Level 4–5 claims per provider.
L4–5 Denial Rate=Denied Level 4–5 claims (coding-related)Total Level 4–5 claims submitted
Reporting grain: one value per cohort per quarter (or rolling 90-day window) Level 4–5 new patient CPTs: 99204, 99205 | Established: 99214, 99215 Denial filter: restrict to denial codes indicating coding/documentation issues Pre / post boundary: each provider's Suki adoption date Exclude: onboarding ramp (default 30 days)
Pseudocode
For each reporting quarter Q: active_providers = providers past ramp period with Suki adoption date before Q For each provider p in active_providers: l45_denied[p] = count of coding-denied Level 4–5 claims in quarter Q l45_submitted[p] = count of total Level 4–5 claims submitted in quarter Q denial_rate[p] = l45_denied[p] / l45_submitted[p] cohort_denial_rate[Q] = MEAN( denial_rate[p] for p in active_providers )
Expected Trends — Algorithms 1 & 3 Compared

ICD-10 coding depth (Algorithm 1) rises post-adoption. Denial rate (Algorithm 3) should hold flat or decline. Together they confirm coding improvement is documentation-supported. Algorithm 2 (Match Rate) follows an early-to-mature trajectory, not a pre/post split.

Suki Data — Scoped Role

Algorithm 2 is the only CM-21 algorithm where Suki provides the primary data. AI-generated ICD-10 codes from the Suki structured-data endpoint (GET /session/{id}/structured-data) are natively available and represent Suki’s direct coding recommendation for each encounter. Comparing these suggestions to final billed codes is a direct measure of Suki’s coding accuracy impact — but requires encounter-to-claim linkage beyond the standard data pull.

For Algorithms 1 and 3, Suki’s role is limited to the adoption boundary (pre/post split) and the active usage flag (cohort denominator). ICD-10 coding depth and claim denial data reside entirely in the EHR and RCM system.
