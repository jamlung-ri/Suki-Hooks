Canonical Measure Algorithm Card

CM-13 — Adoption Behavior and Utilization Rate

U — Use Product Adoption & Utilization Validated Production SQL Also known as: Utilization Rate  ·  Adoption Rate  ·  Scribe Utilization Rate  ·  Active User Count  ·  Engagement Rate

Unit

Unit
Utilization % — Ambient Notes Created ÷ EHR Appointments Scheduled
↑ Higher is better

Utilization is the share of a provider’s (or cohort’s) scheduled EHR appointments in a period for which an ambient note was created by Suki, computed as Ambient Notes Created ÷ EHR Appointments Scheduled, where EHR Appointments Scheduled = EHR Created Appointments − EHR Deleted Appointments. Unlike every other measure in this set, this is entirely Suki-native product telemetry — sourced from Suki’s Admin Center BigQuery tables, refreshed on a 24-hour sync cadence, available at weekly, monthly, quarterly, and yearly grain, and broken out by specialty and by provider.

Gold Standard
Suki Admin Center Utilization metric — SAFE_DIVIDE(ambient_created, appt_ehr_count) from suki-dev.analytics.SukiUserUsage. This is Suki’s own finalized, cross-team-validated metric definition (tracked in a shared BigQuery validation sheet), already run in production against real customer data — not a first-attempt proxy.
Default / Practical
Raw ambient session / note count with no appointment-based denominator. Used only when appt_ehr_count has not yet been reliably ingested for a given customer — e.g., early in onboarding before the EHR scheduling feed into Suki has stabilized.
⚠ Ambiguities to Resolve
  • Literature-to-metric mapping is not one-to-one. Published “Utilization Rate” (Ma 2025: 55%), “Adoption Rate” (AAFP 2021: 60% post-trial), “Scribe Utilization Rate” (Afshar 2025: 65.4%), and “Active user count” are often used interchangeably in papers but map to at least three structurally different Suki Admin Center metrics (Utilization, Adoption Rate, Engagement Rate) with different denominators and different time windows. Confirm which Suki metric a paper’s definition actually corresponds to before reporting any cross-study comparison.
  • Individual vs. cohort denominator capping. Provider-level utilization queries cap the ratio at 1.0 (100%), but cohort/time-series/specialty-level queries do not apply this cap — a provider whose ambient-note count exceeds their EHR-scheduled appointment count in a period (e.g., walk-ins, add-on visits not yet synced, multiple notes per encounter) shows >100% in the aggregate view but is capped at 100% in the per-provider view.
  • Adoption Rate ≠ Utilization Rate ≠ Engagement Rate. Despite the literature corpus treating “Adoption Rate” as an alias of this canonical measure, Suki’s own Adoption Rate metric is a trial-to-paid conversion definition (session activity in a 31–60 day post-first-use window), Engagement Rate is a depth-of-use ratio (≥2 vs. ≥1 weekly ambient sessions), and Utilization is the appointment-coverage ratio. These are three genuinely different constructs currently bundled under one canonical measure — CM-13’s definition should be scoped or split going forward.
  • EHR Appointments Scheduled is Suki-ingested, not a live Epic pull. It is computed from Suki’s own ingestion pipeline (appt_ehr_count), synced every 24 hours — not a real-time EHR query. Discrepancies against a health system’s own scheduling reports should be expected and reconciled before external reporting.

Algorithm

Produces the % of scheduled EHR appointments in a period for which an ambient note was created, at cohort, specialty, or provider grain. This is Suki’s own production Admin Center metric — the queries below are adapted directly from Suki’s internal metric-validation document, not a Regenstrief-derived proxy.

Units in this Algorithm
Primary
Utilization %
The canonical unit for this measure — defined in the Unit card above. Computed at weekly, monthly, quarterly, and yearly grain, and reportable by cohort, specialty, or individual provider.
Secondary
EHR Appointments Scheduled (appt_ehr_count)
The denominator. Computed as EHR Created Appointments minus EHR Deleted Appointments, from Suki’s ingestion of the customer’s EHR scheduling feed.
⚠ This is a Suki-ingested, 24-hour-synced field — not a live Epic query. Confirm ingestion completeness for a given customer before treating small utilization swings as meaningful.
Secondary
Ambient Notes Created (ambient_created)
The numerator. Count of ambient sessions that produced a note, per provider per period, from suki-dev.analytics.SukiUserUsage.
Utilization=∑ Ambient Notes Created (ambient_created)∑ EHR Appointments Scheduled (appt_ehr_count)

Pseudocode — Cohort / Time Series (adapted from Suki Query 3.1)
-- weekly utilization time series, canonical organization WITH raw_counts AS ( SELECT DATE_TRUNC(factDate, WEEK) AS week_start_date, SUM(COALESCE(ambient_created, 0)) AS total_ambient_created, SUM(COALESCE(appt_ehr_count, 0)) AS total_appt_ehr_count FROM `suki-dev.analytics.SukiUserUsage` WHERE organization_id = :org_id AND factDate BETWEEN DATE_SUB(:as_of, INTERVAL 8 WEEK) AND DATE_SUB(:as_of, INTERVAL 1 DAY) GROUP BY 1 ) SELECT week_start_date, total_ambient_created AS ambient_notes, total_appt_ehr_count AS ehr_appointments, SAFE_DIVIDE(total_ambient_created, total_appt_ehr_count) AS utilization -- SAFE_DIVIDE avoids divide-by-zero for weeks with no scheduled appointments FROM raw_counts ORDER BY week_start_date ASC;
Pseudocode — Provider-Level, Capped (adapted from Suki Query 3.3)
SELECT user_id, first_name, last_name, SUM(COALESCE(ambient_created, 0)) AS total_ambient_created, SUM(COALESCE(appt_ehr_count, 0)) AS total_appt_ehr_count, -- Individual providers are capped at 100%; cohort/specialty views are NOT capped (see ambiguity above) LEAST(1.0, SAFE_DIVIDE(SUM(COALESCE(ambient_created, 0)), SUM(COALESCE(appt_ehr_count, 0)))) AS utilization FROM `suki-dev.analytics.SukiUserUsage` WHERE organization_id = :org_id AND factDate BETWEEN DATE_SUB(:as_of, INTERVAL 7 DAY) AND :as_of GROUP BY user_id, first_name, last_name HAVING utilization IS NOT NULL ORDER BY utilization DESC;

Two related Suki-native metrics that other CM-13 literature aliases actually map to. Adoption Rate is a trial-to-paid conversion definition (did a newly onboarded user go on to actually use ambient capture); Engagement Rate is a depth-of-use ratio among already-active users. Neither is interchangeable with Utilization — see the Ambiguities box above.

Units in this Algorithm
Primary
Adoption Rate %
% of users, 31–60 days after their first_usage_date, who logged at least one ambient session (session_count > 0) — conditional on their first_ambient_date falling within 30 days of first product use.
⚠ This is a narrower, trial-window conversion definition — not the same construct as AAFP 2021’s “60% post-trial adoption,” which used a different trial design. Do not directly compare the two rates without confirming window alignment.
Secondary
Engagement Rate
Among users active at least once in a week/month (ambient_cat ≥ 1), the % who were active twice or more (ambient_cat ≥ 2) — a within-active-user depth-of-use signal, computed weekly and monthly from SukiEngagementData.
Secondary
License Status Count
Snapshot count of users by SFDC license bucket (License Active, License Pending, Deactivated), from the most recent sync date — provides the total-user denominator context for adoption and utilization reporting.
Adoption Rate=COUNT(DISTINCT users in cohort WHERE session_count > 0)COUNT(DISTINCT users in cohort)
Cohort = product_type IN ('ASSISTANT','COMPOSE'), status IN ('Live','Conversion Pending','Canceled - Churn') AND first_usage_date within the trailing 365-60 day window of the reference date AND first_ambient_date within 30 days of first_usage_date AND factDate is 31-60 days after first_usage_date (the "did they convert" observation window) Reporting grain: monthly time series; also by specialty for the most recent day
Pseudocode — Adoption Rate (adapted from Suki Query 2.1 / 2.2)
filtered_usage = SELECT * FROM SukiUserUsage WHERE organization_id = :org_id AND product_type IN ('ASSISTANT', 'COMPOSE') AND status IN ('Live', 'Conversion Pending', 'Canceled - Churn') for reference_date in monthly_date_range: cohort = users in filtered_usage WHERE first_usage_date BETWEEN reference_date - 365d AND reference_date - 60d AND first_ambient_date BETWEEN first_usage_date AND first_usage_date + 30d AND DATETIME_DIFF(factDate, first_usage_date, DAY) BETWEEN 31 AND 60 suki_users = COUNT(DISTINCT user_id in cohort) adopted_users = COUNT(DISTINCT user_id in cohort WHERE session_count > 0) adoption_rate[reference_date] = SAFE_DIVIDE(adopted_users, suki_users)
Pseudocode — Engagement Rate (adapted from Suki Query 1.1 / 1.2 / 1.3)
-- weekly grain shown; monthly grain uses mth_ambient_cat instead of wk_ambient_cat SELECT factDate, COUNT(DISTINCT IF(wk_ambient_cat >= 1, user_id, NULL)) AS active_users, SAFE_DIVIDE( COUNT(DISTINCT IF(wk_ambient_cat >= 2, user_id, NULL)), COUNT(DISTINCT IF(wk_ambient_cat >= 1, user_id, NULL)) ) AS engagement FROM `suki-dev.analytics.SukiEngagementData` WHERE organization_name IN (SELECT organization_name FROM org_filter) AND time_grain = 'WEEK' GROUP BY factDate ORDER BY factDate;
Pseudocode — License Status Count (adapted from Suki Query 0.1–0.3)
active_users = COUNT(DISTINCT user_id) WHERE status IN ('Live','Conversion Pending','Admin','Non Revenue') deactivated = COUNT(DISTINCT user_id) WHERE status IN ('Evaluation Abandoned','Canceled - Churn') pending_users = COUNT(DISTINCT user_id) WHERE status IN ('No License') -- All scoped to organization_id and the most recent factDate sync

Suki Data — Scoped Role

This measure is Suki-native telemetry end-to-end, and it is the strongest data foundation of any canonical measure in this set. Every input — Ambient Notes Created, EHR Appointments Scheduled, license status, session counts, and the ambient-usage category buckets — comes from Suki’s own Admin Center BigQuery tables, using query logic that Suki teams have already run in production and cross-validated against each other, not a first-attempt proxy formula.

The one caveat: “EHR Appointments Scheduled” is a Suki-ingested field, not a live Epic query — it depends on the completeness and freshness of a given customer’s EHR scheduling feed as ingested by Suki (24-hour sync cadence), and there is no separate Epic-native version of this algorithm to fall back on. What most needs work is not the SQL but the mapping between this metric family and the literature’s various “adoption/utilization” constructs — see the Ambiguities box above.
